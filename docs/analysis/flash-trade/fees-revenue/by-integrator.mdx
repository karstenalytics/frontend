# Fees by Integrator

Daily trading fees attributed to third-party protocols that integrate with Flash.Trade via Cross-Program Invocation (CPI). Shows which external programs route trades through Flash.Trade and how much fee revenue they generate.

## Data

  {() => {

      useEffect(() => {
        integratorFilter._cbs.add(setLocalPrograms);

        integratorFilter.set(programs);

          onFeeCategoryChange={(cat) => integratorFilter.setCategory(cat)}

## Use Cases

This chart helps you:

- **Track integration growth**: Monitor which protocols are building on top of Flash.Trade
- **Identify top integrators**: See which protocols generate the most fees via CPI
- **Assess integration depth**: Determine if CPI fee revenue is growing or concentrated in a few protocols
- **Spot new integrations**: Detect when new protocols start routing through Flash.Trade

## Methodology

<details>
<summary>Click to expand technical details</summary>

**Integration Detection**

A transaction is classified as integrator-routed when a non-Flash.Trade, non-infrastructure program appears as a top-level instruction invoker alongside or instead of the Flash.Trade program. Infrastructure programs (SPL Token, Associated Token, Memo, System Program, Lighthouse, etc.) are excluded.

Each integrator transaction is further classified by integration type:

- **CPI**: The external program invokes Flash.Trade as an inner instruction (cross-program invocation). The integrator program is definitively the caller.
- **Co-invocation**: Both the integrator and Flash.Trade appear as separate top-level instructions in the same transaction. This pattern is used by protocols whose SDKs compose multi-program transactions (e.g., Jupiter routing a swap leg through Flash.Trade, or Loopscale orchestrating lending alongside position management). While the on-chain data does not prove the direction of integration, these co-invocations typically originate from the integrator's frontend or SDK.

The summary data includes per-integrator CPI vs co-invocation counts so the dominant pattern for each program is visible.

**Fee Extraction**

Per-transaction fees are extracted via CPI event decoding: Swap fees use SwapLogV2 events with per-custody oracle prices and exact token decimals from the pool custody mapping. Perpetual trading fees (OpenPosition, ClosePosition, etc.) use collateral price fields from the corresponding CPI events. Transactions whose Flash.Trade CPI invocation failed (inner program error, outer tx succeeded) are excluded because the instruction is rolled back and no fees are collected.

**Difference from By Pool / By Type Charts**

This chart measures **gross fees at the point of generation** (as reported by CPI events), whereas the By Pool and By Type charts measure **net revenue received by the treasury** (from the reconciled attribution system). Three factors cause the totals to differ:

- **Fee rebates**: Generated fees are gross; treasury receipts are net of rebates
- **Conversion slippage**: Non-USDC fees are converted via SwapFeeInternal at market rates that may differ from the oracle price at generation time
- **Batching**: Fees reach the treasury via periodic MoveProtocolFees events, not per-transaction

As a result, integrator fee totals will be slightly higher than corresponding treasury revenue and should not be directly compared across chart types.

**Program Identification**

Integrator programs are identified by their on-chain address. Names are resolved via a curated mapping of known Solana programs. Unresolved addresses are displayed by their truncated public key.

**Top Transactions Table**
- Shows the 10 largest CPI transactions by fee for the active category (Trading/LP)
- Clicking an integrator in the chart legend filters the table to that integrator's top transactions
- Type and Pool are resolved from CPI event decoding; early transactions may show "-"

**Known Limitations**

- Transaction table stores up to 10 entries per integrator; applying an integrator filter reveals that integrator's individual top 10
- New event versions or pool custodies may temporarily fail to decode until the IDL or custody mapping is updated
- Some integrators may use intermediate proxy programs, appearing as different addresses
- Co-invocation transactions cannot be definitively attributed from on-chain data alone; the external program may be the initiator (e.g., Jupiter routing) or a passive companion (e.g., assertion guards). Known passive programs are excluded via an infrastructure blocklist.

**Update Frequency**

Data is updated once per day via the automated data pipeline.

</details>
